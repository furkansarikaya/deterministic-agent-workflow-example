# Enforcement matrix

| Rule | Classification | Mechanism |
|---|---|---|
| Active task selection | Script-enforced | An empty checked-in `ACTIVE_RUN` reports `active_task=none`; malformed/missing targets fail and implementation commands require an explicit valid task. |
| Valid mode / effective policy | Script-enforced | `agent.sh effective` reads YAML only from the allowlisted mode directory. |
| Invocation role boundary | Script-enforced for CLI lifecycle commands | Default `full_lifecycle` is agent-neutral; explicit `implementation_worker` blocks baseline/freeze/refreeze, later handoff phases, and delivery. |
| Recursive delegation in a worker | Policy-only | The repository has no generic agent-spawn interceptor; worker instructions and vibecosystem policy prohibit delegation. |
| Task, evidence, plan, policy freeze | Script-enforced | SHA-256 values in `RUN.yaml`; `agent.sh verify-freeze` rejects mismatch. |
| Planning freshness | Script-enforced for local Markdown/none sources | `agent.sh freshness` validates base SHA and frozen local task revision; unsupported external adapters block rather than invent state. |
| Handoff patch integrity | Script-enforced | `agent.sh verify-handoff` invalidates VERIFIED/REVIEWED/CODE_DONE evidence when the task-owned patch fingerprint changes. |
| Delivery boundary | Script-enforced local gate | `agent.sh delivery-check` never mutates a remote; it requires current freshness, application-scope integrity, knowledge-transaction integrity, review, verification, and CODE DONE fingerprints. Like `DONE`, it validates application scope and knowledge scope independently (`verify_scope "$id" 1` + `verify_knowledge_scope`) so a knowledge transaction `DONE` already legitimately accepted is not re-rejected by a `delivery-check` call afterward — see `.agents/WORKFLOW.md`'s "Knowledge transaction scope". |
| Application scope and AC mapping | Script-enforced | `agent.sh verify-scope` validates task-introduced application paths against PLAN mappings. |
| Current-run control metadata | Script-enforced | Only a strict known-artifact allowlist inside the current run directory is excluded from application scope; arbitrary `.agents/**` files are not. |
| Dirty-worktree baseline | Script-enforced | `agent.sh baseline` stores `repository.base_sha` and regular-file SHA-256 fingerprints. An unchanged user-owned dirty file is excluded; a later change is checked against scope. |
| Deterministic task branch isolation | Script-enforced for a run whose `RUN.yaml` declares `repository.task_branch` | `agent.sh branch` creates `task/<TASK-ID>-<slug>` from the canonical branch's exact tip (`.agents/config.yaml`'s `canonical_branch`) and records it; `baseline`, `freeze`/`refreeze`, `handoff`, `verify-scope`, and `delivery-check` all fail closed unless the working tree is on that exact recorded branch. `implementation_worker` cannot call `branch` at all. A `RUN.yaml` predating this policy (no `repository.task_branch` key, i.e. `EXAMPLE-001`) is exempt, never retroactively rewritten. |
| Never overwrite/delete a conflicting branch | Script-enforced | `agent.sh branch` refuses to reuse a same-named branch whose tip differs from the canonical base, and never runs `git reset`/`git clean`/a force checkout/branch delete on the caller's behalf; an unsafe switch is left to Git's own refusal (uncommitted changes that would be overwritten). |
| Required run artifacts | Script-enforced | `agent.sh validate` (`validate_run`), runnable at any run phase, not gated on CODE_DONE/DONE. Since it applies the same knowledge-aware `allow_knowledge=1` triad as `DONE`/`delivery-check` for a captured-baseline run (see the DONE/delivery-check/validate row below), it also correctly accepts an already-completed Transaction B rather than re-rejecting it as an unexpected application path. |
| Build/tests/static checks | Script-enforced | `verify.sh` and verification artifact. |
| Wiki structural integrity | Script-enforced | `wiki-lint.sh` reports, never rewrites. Every whole-vault scan (task-reference, duplicate-title, wikilink, and per-page orphan-check) explicitly excludes its own generated `lint-report.md` by name, not only the page-content loop's `$pages` list — the report is control output, never lint input, in every category. Regression: `scripts/agent.sh`'s `wiki_lint_self_scan_test` (`agent.sh test`). |
| Progressive context loading | Policy-only | Mode YAML and shared rules require on-demand retrieval, but repository scripts cannot observe an agent's context window. |
| One implementation worker / separate review phases | Workflow-enforced | Manifest plus distinct review artifacts; platform identity is unavailable to this repository. |
| Wiki no-write during code transaction | Policy-only | Repository scripts can detect scope after the fact but cannot intercept editor writes. |
| Memory, recall, prompt improver, learning writes, swarm | Policy-only in this repository | Deterministic policy denies them; installed host hooks/profile selection remain host-controlled. |
| Credential denial | Platform-enforced when vibecosystem core hook is active | Actual `credential-deny` core hook; repository does not assume it is installed. |
| User confirmation for destructive/external actions | Agent/platform policy | Documents require it; scripts do not authorize actions. |
| Execution topology resolution | Script-enforced, fails closed | `agent.sh resolve_topology` reads `RUN.yaml`'s `execution.topology` (`standalone`/`orchestrated`) or falls back to `.agents/config.yaml`'s `default_topology`; an invalid/missing value on both is a hard failure, never a silent guess. This is a separate concept from agent role — see `.agents/WORKFLOW.md`. |
| Implementation evidence required to leave IMPLEMENT | Script-enforced for a policy-enforced run (`RUN.yaml` has `worker_evidence:`), both topologies | `agent.sh handoff <ID> VERIFIED` calls `verify_worker_evidence`, which fails closed unless every non-exempt frozen scope path has valid RED+GREEN/FIX evidence bound to the *current* frozen task/evidence/plan hashes AND authored by the role `agent.sh expected_implementation_owner` resolves for the run's current topology. A run frozen before this policy (no `worker_evidence:` key) is exempt, never retroactively rewritten — same pattern as `repository.task_branch`. |
| Implementation-evidence structural/task/freeze/role binding | Script-enforced | `agent.sh worker-evidence` only accepts the role the resolved topology expects (`full_lifecycle` under `standalone`, `implementation_worker` under `orchestrated` — the other role is refused at record time), refuses an out-of-scope target, a `RED` record without `result: fail` and a specific `expected_failure`, and a `GREEN`/`REFACTOR`/`FIX` record without `result: pass`; `verify_worker_evidence` additionally rejects a file whose `task_id`, `task_sha256`/`evidence_sha256`/`plan_sha256`, or authoring role no longer match the current run/freeze/topology (stale, cross-task, or wrong-owner evidence). |
| Implementation-owner identity proof | Declared, optionally cross-checked | `AGENT_ROLE` remains a declared claim in both directions (same limitation as the pre-existing role boundary below) — a `full_lifecycle` session could still export `AGENT_ROLE=implementation_worker` itself under `orchestrated`, exactly as it could claim `AGENT_ROLE=full_lifecycle` under `standalone`. When a local Codex session log directory is discoverable, `verify_worker_evidence` additionally checks a recorded `codex_session_id` against it; this narrows but does not close the gap. |
| TDD exemption validity | Script-enforced (structural) | `verify-worker-evidence` rejects an empty, too-short (<20 chars), or stock-phrase `tdd_exemption` in `PLAN.md`. Semantic appropriateness of a *valid-looking* exemption remains a reviewer judgment, recorded in `review/code-review.md`, not something a script can assess. |
| Task Completion Report required before DONE | Script-enforced for a policy-enforced run (`RUN.yaml` has `completion_report:`) | `agent.sh handoff <ID> DONE` fails unless `completion_report.published = true`, `execution.knowledge_state` is `KNOWLEDGE_DONE`/`not_applicable`, and `agent.sh verify-completion-report` (which re-invokes the adapter's own `verify` operation) passes — never satisfied by marking DONE first. |
| Task-integration adapter boundary | Script-enforced structure, policy-only content | `agent.sh` only validates the report's minimum section structure and delegates `publish`/`verify` to `.agents/task-integrations/<name>.sh`; it never encodes a specific tracker's API. See `.agents/task-integrations/README.md`. |
| Canonical worker invocation path (orchestrated topology only) | Script-enforced fail-closed, no fallback | `scripts/worker-run.sh` is this reference repository's one vendor adapter for `implementation_worker`, wired to Codex (`codex exec`) — a different consuming project's adapter could target a different tool; the generic control plane does not require Codex specifically, only that *some* `implementation_worker` invocation path exists when a run's topology is `orchestrated`. A missing `codex` binary or a non-zero `codex exec` exit is a hard failure with a preserved log under `.agents/runs/<ID>/worker-evidence/`, never a silent `full_lifecycle` implementation fallback; `worker-run.sh` also refuses to run at all against a run whose resolved topology is `standalone`. Model/reasoning-effort are not pinned by default — both are read from the operator's own `~/.codex/config.toml` unless `--model`/`--effort` is explicitly passed. It grants `codex exec --sandbox workspace-write` a single `--add-dir` scoped to exactly the active run's own `worker-evidence/` directory (the one path that sandbox otherwise denies writes to, being dot-prefixed) — never a broader `.agents/**` grant. See `.agents/WORKFLOW.md`'s "Worker evidence and the sandbox boundary". |
| Worker evidence write is fail-closed | Script-enforced | `agent.sh worker-evidence` verifies its own write actually produced a non-empty, structurally valid evidence file before reporting success; a denied/failed write (sandbox or otherwise) removes any partial file and aborts via `fail` (non-zero exit), never a false "recorded" message. Regression: `scripts/agent.sh`'s `worker_evidence_write_failure_test` (`agent.sh test`). |
| Knowledge transaction (Transaction B) scope | Script-enforced, fails closed | `.agents/config.yaml`'s `knowledge_scope_root` is the sole allowlisted directory prefix for post-CODE_DONE wiki writes; `agent.sh verify-knowledge-scope` (also run automatically inside the `DONE` handoff transition) requires every changed path under that root to coincide with `execution.knowledge_state = KNOWLEDGE_DONE`, rejects a knowledge-scope diff without a recorded-complete transaction (including a mismatched `not_applicable`), and rejects `KNOWLEDGE_DONE` recorded with zero actual diffs. A path outside the root is always application scope, never knowledge scope, regardless of `knowledge_state`. See `.agents/WORKFLOW.md`'s "Knowledge transaction scope"; regression: `scripts/agent.sh`'s `knowledge_scope_test` (`agent.sh test`). |
| DONE, delivery-check, and validate require both application-scope and knowledge-scope integrity | Script-enforced | `record_handoff`'s `DONE` case checks `handoff.code_done_patch_sha256` (application scope, unchanged mechanism) and `agent.sh verify-knowledge-scope` (knowledge scope) independently; either failing blocks `DONE`. `delivery_check` (called after `DONE`, as a real delivery attempt does) and `validate_run` (`agent.sh validate`, callable at any phase) both mirror this exactly for a captured-baseline run: `verify_scope "$id" 1` + `verify_knowledge_scope "$id"` + `verify_handoff "$id" 1`, so a knowledge transaction `DONE` already accepted is not re-rejected as "unexpected" merely because `delivery-check`/`validate` run afterward. `verify_scope`'s opt-in second parameter (`allow_knowledge`) and `verify_handoff`'s opt-in second parameter (forwarded to `verify_scope`) are used *only* by `DONE`, `delivery_check`, and `validate_run` — every earlier phase (IMPLEMENTING/VERIFIED/REVIEWED/CODE_DONE) and every other caller (the `verify-scope`/`verify-handoff` CLI commands) stay strict, so a knowledge-scope write attempted before CODE_DONE is rejected exactly as before this existed. `validate_run` skips both calls entirely for a historical-reference run (no captured baseline) — `verify_scope`/`verify_knowledge_scope` fail outright for such a run rather than passing trivially, so calling them there would be a regression, not a fix; `verify_handoff` alone (still called, still with `allow_knowledge=1`) already short-circuits correctly for that case via its own historical-reference check. Regression: `scripts/agent.sh`'s `delivery_check_knowledge_scope_test` and `validate_knowledge_scope_test` (`agent.sh test`) reproduce the exact real-world sequence (CODE_DONE → KNOWLEDGE_DONE with a legitimate wiki diff → DONE → delivery-check/validate succeed) plus the same application-scope/knowledge-scope failure-closed cases `knowledge_scope_test` proves for `DONE`. |

Never describe policy-only behavior as technically disabled.

## Evidence strength

Hashes, policy selection, `repository.base_sha`, and baseline fingerprints are machine-verifiable. Worker roles, worker identity, and reviewer/verifier independence are declared workflow evidence unless the host platform supplies auditable identities. Baseline hashes prove that a file changed after task start, not that an authorized edit semantically preserved every part of user-owned work; reconciliation remains an agent and review obligation.

`EXAMPLE-001` is a historical reference with `baseline.status: legacy_not_captured`; validation accepts that explicit marker, while live scope verification is intentionally unavailable for it. Its recorded policy hash is retained as historical evidence; only this marker permits reporting that the current policy has since changed. Live runs always fail a policy-hash mismatch.
